# Postgres persistence with Drizzle

The project selected `ts-drizzle-postgres`. Every context that declares a
store out port (`<Feature>Store`) is persisted in Postgres through Drizzle, in
its own Postgres schema. `docs/architecture/persistence.md` in the project is
the rulebook; this note says who writes which file and how the gates treat
them.

## Files

Under `contexts/<context>/`:

| File | Owner |
|---|---|
| `drizzle.config.ts` | generated; no role writes it |
| `src/adapters/out/drizzle/drizzle-database.ts` | generated: `DrizzleDatabase`, Drizzle's generic Postgres database type |
| `src/adapters/out/drizzle/schema/<context>.schema.ts` | generated: the context's `pgSchema` |
| `src/adapters/out/drizzle/schema/<area>.ts` | skeleton, then the builder's: the area's tables |
| `src/adapters/out/drizzle/<area>/<feature>.store.ts` | skeleton, then the builder's: `Drizzle<Feature>Store` |
| `src/adapters/out/drizzle/<area>/<concept>.mapper.ts` | the builder's |
| `src/adapters/out/drizzle/migrations/**` | generated by the architect's `generate_artifacts` gate only |
| `src/adapters/out/drizzle/drizzle-test-database.test-support.ts` | generated: the store tests' database |
| `src/adapters/out/drizzle/<area>/<feature>.store.test.ts` | the test-writer's |

The root `docker-compose.yml`, `.env.example`, `scripts/check-db.ts` and
`scripts/db-migrate.ts` are generated project config.

## Builder: stores and mappers

- A store implements exactly its feature's store port. Its constructor stays
  `(private readonly db: DrizzleDatabase)`: the composition root passes one
  shared database, and it picks the driver (`drizzle-orm/bun-sql` for Bun
  apps, `drizzle-orm/node-postgres` for Lambdas). A store never imports a
  driver, and nothing outside `adapters/out/drizzle/` imports Drizzle.
- Query with Drizzle's query builder over the table objects in `schema/`
  (`db.select().from(notes)`, `db.insert(notes).values(...)`). The database
  carries no relational schema, so `db.query.*` is not available.
- Tables go in `schema/<area>.ts`, created in the context's schema:
  `export const notes = projectManagement.table("notes", { ... })`. Tables
  are an adapter detail and need not match the domain objects. References
  between areas are foreign keys; references to other contexts are plain id
  columns.
- A mapper, `<concept>.mapper.ts`, turns a row into a domain object and back.
  It rebuilds every value object with its factory's `parse`, and throws when
  one fails: a stored row that does not parse is corrupt data, never a
  business failure. Mappers are plain functions, for example
  `toNote(row): Note` and `toNoteRow(note): typeof notes.$inferInsert`.
- Two stores with the same code today stay separate classes.

## Test-writer: store tests

A store test runs the feature's shared conformance suite
(`application/<area>/<feature>/<feature>.store.test-support.ts`) against the
Drizzle store, inside the generated helper:

```ts
import { describeDrizzleStore } from "../drizzle-test-database.test-support.ts";

describeDrizzleStore("DrizzleCreateNoteStore", (db) => {
  createNoteStoreConformance(() => new DrizzleCreateNoteStore(db()));
});
```

The helper starts one Postgres container per test run on first use, applies
the context's migrations, and empties the context's tables before each test.
Seed rows a test needs through `db()` and the tables in `schema/`. Call `db()`
inside a test, never while the block is declared. Unit, handler and
in-adapter tests never touch the database.

## Architect: migrations

After the builder changes `schema/`, call `generate_artifacts`. It generates
the next migration for every context into a throwaway copy first and writes
only when every context succeeded, so a failure leaves all history as it was.
Review the SQL before `green_gate`; a wrong migration is a wrong schema, so
route the fix to the builder and generate again.

A renamed column or table is ambiguous: Drizzle must ask whether it is a
rename or a drop-and-create, and the gate refuses with nothing written. Make
the change in two steps (add the new column, generate, then drop the old one
and generate again), or escalate to the user, who runs
`bunx drizzle-kit generate` in that context in a terminal.

## Docker

Store tests need a container runtime (ADR 2026-064). Without one, red skips
the store tests and logs why; every other level still runs. Green refuses
while store tests exist and no container runtime answers: it never passes by
skipping them.

## Project commands

- `bun run db:up` starts the local Postgres; `bun run db:migrate` applies
  every context's pending migrations to `DATABASE_URL` (from the root `.env`,
  copied from `.env.example`).
- `bun run check:db`, part of `check`, verifies that every context's committed
  migrations match its schema, without writing anything.
