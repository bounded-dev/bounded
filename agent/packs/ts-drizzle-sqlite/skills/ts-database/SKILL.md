# Persistent data

The project selected `ts-drizzle-sqlite`. It has a local SQLite database through
Drizzle. The product owns its tables and data rules; this capability supplies
the driver and migration workflow.

Describe storage needs in the product design. Put domain meaning and validation
in domain components, and expose a repository interface to callers. Keep table
definitions and SQL details in the persistence implementation. The UI should
consume service read models, never query tables or duplicate a list of domain
values. A database schema does not decide the public service contract.

The builder changes `src/db/schema.ts` and implements repositories under
`src/db/` against the domain interfaces. Every schema change needs a reviewed
SQL migration generated by `npm run db:generate`. Commit both the SQL file and
Drizzle's `meta/` files under `src/db/migrations/`. Never use `drizzle-kit push`
for tracked product data; it bypasses the versioned history.

The project commands are:

- `npm run db:generate`: derive the next SQL migration from the current schema.
- `npm run check:db`: detect schema drift or broken migration history without
  changing the project's database; it generates into a temporary copy and
  applies the committed migrations to a fresh temporary SQLite database.
- `npm run db:migrate`: apply only pending committed migrations to
  `DATABASE_URL` (default `file:./data/app.sqlite`).

Call `migrateDb()` before the service accepts requests and before a data refresh
imports rows. Failed migrations must stop startup or refresh. Keep database
files out of Git; the SQL history belongs in Git. A later backend can supply a
different driver and configuration without changing the domain interfaces.

The builder's gated toolset has no shell. After the builder changes the schema,
the architect calls `generate_artifacts`. That gate invokes this pack's
migration generator and logs the result. The architect reviews the generated
SQL before green and routes any schema or migration corrections to the builder.
The delivery gate blocks if the schema and committed migrations differ or the
migrations cannot be applied from an empty database.
