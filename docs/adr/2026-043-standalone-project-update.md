# 2026-043: Standalone project update and one-generation rollback

**Status:** accepted. Amends [ADR 2026-033](2026-033-standalone-command-routing.md), [ADR 2026-037](2026-037-standalone-claude-code-hooks.md), [ADR 2026-038](2026-038-managed-pack-type-projection.md), [ADR 2026-040](2026-040-standalone-project-check.md) and [ADR 2026-041](2026-041-standalone-pi-worker.md).

## Decision

`bounded update` moves a project to the exact version of the verified installed executable that runs the command. It does not select or fetch a release. The project configuration stays byte-for-byte intact. A transition from a prior standalone release verifies its installed receipt and release files. A transition from a published npm installation is admitted only when its generated host files, configuration and complete installed package closure match the exact published 3.3.0 default under [ADR 2026-044](2026-044-published-npm-runtime-closure.md). Unknown npm installations and imported packs outside that closure refuse. Stable releases may update within one major version without downgrading; prereleases require a separately reviewed compatibility path.

The update holds the project update writer, then the managed-pack writer. It prepares the target host files and any managed type projection under those writers, compiles and validates the exact target configuration for every installed host, and records its source file inventory. A durable update journal records exact old and new bytes and modes for Bounded-owned files, the managed directory inventories and the previous rollback record. New host files and the managed projection publish before the project version pin; the pin publishes last. Standalone generated host entries, the CLI dispatcher, `check`, `add` and a running Pi worker refuse while the marker exists. Previously published npm host code cannot gain this marker check; a loaded npm Pi session must be restarted after migration.

Recovery uses the journal as the single cross-file transaction authority. It authenticates both release identities, generated host forms and managed projection snapshots against the verified release and pack store before a rollback write. An npm source additionally requires a reverified old installed closure and `node --version` reporting Node 22.18 or newer before old Node hooks may be restored. That command is an environment prerequisite, not independent proof that the executable on a user's `PATH` is trustworthy. Each live owned path must match either its recorded old or new state. A complete target state is accepted only after target verification; otherwise recovery restores and verifies every old file and directory. User edits, links, missing dependencies or uncertain states retain the marker and refuse. The journal is bounded to 20,010 owned files and 768 MiB of serialized data before parsing. The high byte cap accommodates two base64 snapshots of a managed projection and makes recovery memory use correspondingly high.

After a successful update, one private rollback record retains the immediately previous generation. `bounded update --rollback` verifies that record, the old runtime and the unchanged current project, then publishes the inverse transaction with the same marker and pin-last order. A successful rollback consumes the record. A later successful update replaces it. Rollback does not reinstall an executable or run a package manager. Projects with edited owned host, pin, configuration or managed files refuse automatic rollback and keep their current state.

The newly shipped Node CLI refuses to rewrite a project already pinned to the standalone executable. A previously published Node CLI cannot be changed retroactively. The published 3.3.0 CLI's `update --no-upgrade` can replace Pi's loader with its npm form while leaving the standalone pin and Claude hooks intact. After migration, users must run the installed standalone `bounded` command.
