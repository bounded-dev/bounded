# 2026-011: Undoing what shell commands change in watched files

**Status:** accepted.

## Decision

- **A core extension point, `watchedPaths`**, on the core pack: files a shell
  command must not change (`match`, `except`, `changes`, `why`,
  `redirect`), checked by `WatchedPath.parse`. Mechanism only: packs (the
  path gate, after its merge) and projects contribute the paths.
- **Only forbidden changes are undone.** A watched path names the changes a
  command must not make to its files, `create`, `modify` and `delete` (every
  one when left out); the path gate gives each the writes its rule denies.
  After a command, a created file is moved aside only when create is
  forbidden, a modified one restored only when modify is, a deleted one
  restored only when delete is; any other change is the command's to make,
  and is neither undone nor reported. So a rule denying modify and delete on
  `migrations/**` lets a command add a migration, as the Write tool may.
  Every watched path that matches a file counts, as every rule does in the
  path gate: a change any of them forbids is undone, and is reported under
  the first that forbids it, so a looser path (`generated/**` forbidding
  only create) never hides a stricter one (`generated/a.ts` forbidding
  modify). The adapters name every rule that watches a file, and after a
  command drift asks the watched-files port again which rules watch each
  changed path (`rulesWatching`), from the rules composed now: it never
  trusts the rules a snapshot stored, so a snapshot loosened by hand cannot
  let a forbidden change stand.
- **A new event, `ToolResult`**: a finished tool call (role, tool, effects,
  `ok`, `callId`), parsed like a tool use. `ToolUse` gains an optional
  `callId`, so a snapshot taken before a call can be found after it. It is
  not part of `Event`: guards judge calls before they run; results are
  checked for drift.
- **An application feature, `drift/watch-shell`**, with two operations,
  `snapshot` before an allowed call with an `execute` effect and `verify`
  after it, and two async out ports so the core names no technology:
  `WatchedFiles` (hash the watched files, name the checked-out commit and
  what it holds, copy a file, restore one file from a copy or a commit,
  move created files into quarantine) and `ShellSnapshots` (keep a snapshot per call id, given back
  as stored). The judge's new check before allowing runs the
  snapshot, so a failure refuses the command and the refusal is what is
  recorded.
- **Restore what was there, never another version.** A snapshot keeps each
  watched file's SHA-256 and size and how to put it back: by reference to
  the commit when it matches it, else a copy of its bytes (1 MB a file, 10 MB
  in all), else nothing. Restoring uses the copy or the commit, with the
  executable bit; a file kept by nothing is reported and left as the command
  left it. So uncommitted and untracked work survives.
- **Never delete.** A file the command created (absent from the snapshot) is
  moved into `<state>/bounded/<root hash>/quarantine/<time>/<path>` (0700,
  0600), and the message and the record name the directory. So a snapshot
  entry removed by tampering costs no file.
- **File-backed snapshots, out of the project.** Claude Code runs each hook
  as its own process, so snapshots are files in the user's state directory,
  `$XDG_STATE_HOME/bounded/<sha256 of the root>/snapshots/` (or
  `~/.local/state`), one per call named by a hash of its id, directories 0700
  and files 0600. They expire after a day and are swept on every save. An
  in-memory store serves tests and single-process hosts.
- **Detection over hiding.** The same user can still change a snapshot, so
  the handler checks it before trusting it (form, hashes, copies against
  hashes, references against the commit). A shell command's result whose
  snapshot is missing, unreadable or altered is compared with the last
  commit, reported and recorded, and nothing is restored, since earlier work
  can no longer be told from the command's; a missing snapshot with nothing
  different from the commit says nothing.
- **Fail closed.** No call id, or reading failing before the command, refuses
  it. After the command, any failure to check or restore, or a restore that
  leaves a file different from the snapshot, is reported loudly to the agent
  and recorded.
- **File system adapter**: runs on any runtime (pi runs the core under node;
  no Bun API in context runtime code, an architecture rule). In a git
  repository it takes the files git lists (tracked, untracked and ignored,
  ignored directories walked only where a rule may lead); outside git it
  walks only the directories a rule's fixed leading part leads to. It never
  looks inside `node_modules` or `.git` at any depth (protecting
  dependencies is out of scope), matches with picomatch (`match` ignoring
  case, as the path gate does; `except` exact), never follows a link (a
  matched link is recorded by where it points and kept by its hash alone),
  hashes with node:crypto, and reads commits with git (`rev-parse`,
  `ls-tree`, `cat-file --batch`); restoring writes the file's bytes and
  executable bit, so git's index is left alone.
- **Hosts** call `judge(toolUse)` and `afterTool(toolResult)` on the
  `ProjectJudge` from `openProject`.

## Deviations from the example

The feature's in port has two methods (before and after a call), not one
`execute`; they share the snapshot. It reuses judge-event's `GuardLog`,
`Clock` and `DecisionIds` ports.

## Consequences

A shell command's changes to watched files never survive it unnoticed:
they are restored as they were, or reported (a file too large to copy, or a
snapshot that was tampered with) and recorded. Nothing stops a command reading
protected files while it runs, and the same user can still change a snapshot;
detection, not the snapshot's location, is the control.
