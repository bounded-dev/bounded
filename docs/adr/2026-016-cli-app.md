# 2026-016: The `bounded` command is its own app, bounded-cli

**Status:** accepted (the maintainer's decision, in the review of issue #65's
first slice).

## Decision

- **The CLI lives in `apps/cli`, package `bounded-cli`, bin `bounded`.** It
  is an app like the host adapters. It may do I/O and use libraries. It
  reaches the core only through its export paths and its declared
  dependency on `bounded`, and it imports no other app: it finds host
  installers at run time through the core's `HostInstallerSource`
  ([ADR 2026-015](2026-015-host-installers.md)).
- **The core keeps the mechanism and names no package manager.** It keeps
  the `project-setup` features (`init-project`, `update-project`), their
  ports, the adapters that implement them (`FileSystemProjectSetupFiles`,
  `NodeModulesHostInstallerSource`) and the installer conformance export.
  It loses the bin. Everything that spawns processes, chooses a package
  manager or rewrites `package.json` is in the app.
- **Installing and upgrading hand over to the installed version.**
  - `bounded init --from <dir> [--host <host>]...` is the first install, run
    through npx before the project has any bounded package. It adds
    `bounded`, `bounded-cli` and `bounded-<host>` as devDependencies, for
    each host found by its directory (`.claude/`, `.pi/`) or named. It then
    runs the installed `bounded init`.
  - `bounded update --from <dir>` upgrades the same packages, then runs the
    installed `bounded update --no-upgrade`.
  - Every later version keeps accepting `bounded init` and
    `bounded update --no-upgrade`. That is the contract that lets each
    release bring its own install and update logic.
- **The package manager** is the lockfile's; else `package.json`'s
  `packageManager`; else the one running the command
  (`npm_config_user_agent`); else npm.

## Why

The core owns mechanism, never content. Package managers, npx and the
layout of `node_modules/.bin` are a distribution's concerns, as host
adapters are a host's. Keeping them out of the core keeps its rules
(no I/O beyond its adapters, nothing tool-specific) and the pinned list of
its export paths unchanged. A separate package also lets the CLI be
upgraded and handed over to like any other.

## Consequences

- While the npm package `bounded` is the legacy 2.x
  ([ADR 2026-014](2026-014-legacy-harness-moves-to-legacy.md)), npx must
  be given the bounded tarball beside bounded-cli's
  (`npx -p bounded-<v>.tgz -p bounded-cli-<v>.tgz bounded init --from <dir>`).
  `init --from` makes `package.json` override `bounded` with the local
  tarball, and `update --from` moves that override to the new tarball.
  Once published, `npx bounded-cli init` will do.
- The host-to-package convention, `bounded-<host>`, is the app's, used
  only to choose what `init --from` installs. Which installers run is
  still decided by the packages' `./host-installer` exports.
- With bun, installing rewrites the specs in `package.json` and runs
  `bun install`, because `bun add` cannot replace one tarball dependency
  with another. npm, pnpm and yarn use their own add commands. Only bun is
  exercised end to end.
