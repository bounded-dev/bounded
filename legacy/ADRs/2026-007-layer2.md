# 2026-007: Layer 2 — canonical commands, language packs, activation scope

**Status:** accepted

## Decision

The harness stays language-agnostic; multi-app leverage lives in Layer 2,
organized by **activation scope** rather than directory taxonomy:

1. **Canonical commands.** Every project declares `check`, `test`, `build`,
   `lint`; any agent session in any project looks for these names first.
   The vehicle is a TS project template repo (committed
   `.pi/settings.json`, project AGENTS.md, wired scripts).
2. **Language packs.** Language-specific capability lives in
   `packs/<lang>/` — flat pi packages loaded via local path
   (`"./packs/ts"`). On-demand skills and scaffolder scripts only; never
   extensions or root AGENTS.md content. Skills are self-contained (no
   cross-pack `../../` references) with domain-prefixed names
   (`ts-new-value-object`).
3. **App type = template first.** Always-on app-type constraints
   (hexagonal layout, validated routes, value-object primitives) are
   vendored into each project's AGENTS.md + lint/architecture config at
   creation time. A stack earns a `packs/<stack>` entry only when it
   accumulates reusable cross-project procedures.
4. **Skills split.** `agent/skills/` here: harness-procedural. Standalone
   utilities authored in `bounded-dev/skills` are **vendored** (copied) into
   `agent/skills/`, not referenced as a sibling package (ADR 2026-012).
   App-building skills live in packs and templates.

## Why

- Retrofitting conventions across N live projects is the most expensive
  change on the horizon; fixing names and placement now is near-free.
- Ecosystem standards layer by *when context fires*, not where it sits in a
  tree: Agent Skills (flat, self-contained, description-triggered), Cursor
  rules (activation modes), AGENTS.md (nearest file wins). Glob-triggered
  rules have no pi equivalent — lint/architecture tests are strictly better
  enforcement for those anyway.
- pi's local-path package mechanism is the same seam a separate repo would
  give; splitting a pack later = move a directory + one settings line, so
  monorepo tooling is deferred.

## Consequences

- `packs/ts/` starts near-empty; content is extracted from real app work,
  not designed up front.
- Split trigger for a pack: a second language pack exists and it is stable,
  or it needs independent versioning/sharing.
