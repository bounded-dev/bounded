# 2026-054: Project config is generated from the packs, never written by a role

**Status:** accepted

## Decision

No role may write project configuration: the compiler config, the package
manifest and lockfile, the test-runner config, or any other file the composed
packs name as config. This replaces the architect's config write access from
ADR 2026-052. The `architectWriteFiles` data field is removed. The architect's
pack-contributed write zone is now only the contract globs, passed to the path
policy as `Ctx.contractGlobs` like the blind roles' globs. A config diagnostic
has no owner and routes to `orchestrator`.

In a project-local installation (`bounded init`), config is a pure function of
the composed packs, computed by the TypeScript pack
(`agent/packs/ts/scripts/project-config.ts`):

- The package manifest comes from `project-package.ts`, the same writer
  initialization uses: the template, every pack's `pins` and `projectScripts`,
  and a new data field, `projectCheckScripts`. It lists script names folded
  into `check` in composition order. The ts pack pins `ts-morph` and folds
  `check:surface`. The ts-web pack folds `check:build`. The generated
  manifest is therefore already the delivered one, and delivery's manifest
  steps find nothing to change.
- The lockfile must hold exactly the closure of the generated pins.
- Other files come from each pack's `projectConfigFiles` reference copies. The
  ts-web pack now ships its Vite config and its `index.html` this way,
  byte-identical to what its generator writes. A test pins them. The bundler
  reads `index.html` from the root as its build entry, so ts-web also lists it
  in `projectConfigNames`.
- Another new data field, `projectConfigNames`, lists root file-name globs
  that count as config. A matching file that no composed pack generates is
  drift. An example is a `vitest.config.ts` in a project whose packs generate
  none.

- `projectShippedFiles` maps project paths to pack files copied verbatim.
  The ts pack ships `scripts/surface-check.ts` at init, so `check:surface`
  never waits for delivery. The shipped file is drift-checked like config,
  because the project's own check runs it.
- `projectNestedConfigNames` lists names that count as config at any depth.
  The ts pack lists `package.json`, `tsconfig*.json` and `jsconfig*.json`.
  Node reads the nearest `package.json` for each file (module type,
  `imports`), and the test runner's transform reads the nearest `tsconfig`.
  Root-only names such as the test-runner, bundler and `.npmrc` config are
  the ones the tools load from the project root; they do not search
  subdirectories.
- `projectDependencyDirs` lists the directory names installed dependencies
  resolve from. The ts pack lists `node_modules`. Node, the type-checker and
  the bundler resolve a nested one before the root's, so a role that wrote
  `src/node_modules/zod/` would replace a contract dependency. The drift walk
  skips these, `.git` and `.bounded` only at the root. Any of them deeper is
  drift. Sync removes it.

**Path policy.** Every role is refused a write to any path with a `.git` or
`.bounded` segment at any depth (core), or with a segment the packs list in
`projectDependencyDirs`, or whose file name matches
`projectNestedConfigNames` (pack data, via `Ctx.writeProtection`). A role is
refused at the write, rather than halting every later gate on drift. An
unreadable composition refuses every write. Matching ignores case.

**Drift check.** Every gate or tool that runs the test runner, the
type-checker or the bundler calls `configDriftBlock` before anything else:
design, red, green, deliver, run-tests, typecheck, mutation-score and the
web render. The two spawning primitives, `runTests` and `typecheck`, also
refuse by themselves, so no caller can spawn over drift. Green spawns
through them on the live tree, so it is re-checked at the spawn. Red runs in
its shadow copy, which those primitives cannot judge. It therefore re-checks
the live tree after the copy and before the spawn. The shadow copies every
root file `projectConfigNames` matches, so a web red runs with the Vite
config. If any config file is
changed, missing or not generated by a composed pack, the tool refuses, logs
the drift and prints `route → orchestrator`. The block applies to every
change, including one the user made by hand.

**Sync.** `bounded sync-config` is a ts pack project command. It rewrites every
generated file and derives the lockfile from the project's own lockfile, or
from the harness source lock when the pins have moved on. It also removes
config files that no pack generates. It computes everything before it writes
anything. When it changed anything, or a project dependency tree is missing,
it then runs the composed packs' `projectSetupCommands`. These install only
from the lockfile and never run lifecycle scripts. This is the one supported
reinstall after the first setup.

**The lead runs sync, after the user agrees (amended by ADR 2026-072).** No
role can reach it: a bound role's shell runs only `bounded gates <gate>`.
Sync overwrites what is on disk, which may be the user's deliberate edit, and
its reinstall is one the lead's setup deliberately refuses after the first
run (ADR 2026-051), so it needs the project owner's agreement. The team lead
runs it as `bounded lead sync-config <issue>` (pi: `lead_sync_config`), in
that ticket's worktree, only once the user agrees; the user never runs it.

**Delivery changes no generated config.** In a generated project, a delivery
step that would pin, fold a script or install is a block routed to the
orchestrator. An unpinned dependency is a pack defect, and a missing install
is restored by the team lead's `sync-config` once the user agrees (ADR
2026-072). Delivery re-runs the drift check last.

**Launcher.** The project-local `bounded` dispatches exactly the composed
packs' `projectCommands`. A name that shadows a core subcommand is refused at
init.

**No add-dependency command.** A dependency the project needs must be a pack
pin.

## Why

Run 9 gave the architect config writes so that the skill's instruction to fix
config itself ("orchestrator — also you") worked. But the test-runner config
is code that `run_tests` and the red and green gates execute. The architect
could therefore change what the gates run. The gates are the product, so their
inputs must be deterministic.

## Consequences

- An initialized project's `npm run check` no longer depends on delivery.
  Before the first feature it is still red: the type-checker finds no
  inputs, the test runner finds no tests, and the surface check refuses a
  project with no contract. Each of those is deliberate.
- The check does not apply to projects whose config the packs never generated:
  adopted repositories and global-harness arms. There, only the path policy
  keeps roles out of config.
- No `bounded update` exists yet. When one lands, it must carry a source lock
  for any new pins; otherwise the sync refuses and writes nothing.
